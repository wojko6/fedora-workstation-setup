# Worklog — 2026-10-01

## Fedora syslog-ng / Tailscale boot readiness

A repeatable boot-order failure was investigated on the physical Fedora
workstation hosting the ASUS Edge syslog-ng collector.

### Observed failure

The collector binds TCP/6514 only to the workstation's Tailscale IPv4 address.

On two consecutive boots, `syslog-ng.service` started before that address was
assigned to `tailscale0`. The unit already declared ordering after
`tailscaled.service` and `network-online.target`, but that ordering was not
sufficient: systemd considered `tailscaled.service` started before the
Tailscale backend had reached its usable Running state and before the node IPv4
address was present.

The failure signature was:

```text
Error binding socket
Cannot assign requested address (99)
Error initializing message pipeline
```

The package unit's `Restart=on-failure` policy then retried quickly until the
systemd start limit was hit. A later manual start succeeded once Tailscale was
fully ready.

### Remediation

The accepted local drop-in now gates syslog-ng startup with Tailscale's own
readiness command:

```ini
[Unit]
Wants=tailscaled.service network-online.target
After=tailscaled.service network-online.target

[Service]
ExecStartPre=/usr/bin/tailscale wait --timeout=60s
ExecStartPre=/usr/bin/tailscale ip --assert=<current-node-tailscale-ip>
RestartSec=15s
```

The public repository does not store the real Tailscale IPv4 address. The
installer derives the current node IPv4 locally when the private
`/etc/syslog-ng/conf.d/asus-edge-collector.conf` is present.

Tailscale documents `tailscale wait` specifically for services that need to
bind to a Tailscale interface or IP. Fedora's installed Tailscale 1.98.8 CLI
provides the command, while the tested RPM did not ship
`tailscale-online.target`, so the drop-in calls the CLI readiness primitive
directly.

### Controlled reboot validation

After installing the readiness guard, a physical reboot produced the intended
sequence:

```text
tailscaled.service started
  -> Tailscale backend reached Running
  -> Tailscale IPv4 became available
  -> syslog-ng ExecStartPre checks passed
  -> syslog-ng started
  -> TCP/6514 listener present on the Tailscale IPv4
```

Observed acceptance state after reboot:

```text
syslog-ng ActiveState=active
syslog-ng SubState=running
Result=success
NRestarts=0
both ExecStartPre commands status=0
TCP/6514 listener present on Tailscale IPv4
current-boot bind/startup error search: empty
```

The service started only after Tailscale reported its peer API on the node
address and transitioned to Running.

### Scope and boundaries

This validates the boot-readiness dependency for the existing local collector.
It does not publish the collector's private Tailscale address, client
certificates, CA material, or other private logging configuration.

The unrelated package-unit warning about an unset `SYSLOGNG_OPTS` environment
variable remains a separate cleanup item because it did not cause the bind
failure and the service reached `Result=success`.


## SELinux / syslog-ng execmem root-cause analysis

A current-boot `ausearch` review showed that each syslog-ng process start
generated one enforced SELinux denial:

```text
avc: denied { execmem }
comm="syslog-ng-main"
scontext=system_u:system_r:syslogd_t:s0
tcontext=system_u:system_r:syslogd_t:s0
tclass=process
permissive=0
```

The investigation intentionally kept SELinux in Enforcing mode and did not
generate an `audit2allow` policy.

Controlled probes established:

```text
minimal syslog-ng without scl.conf -> +1 execmem AVC
minimal syslog-ng with scl.conf    -> +1 execmem AVC
syslog-ng --version                -> +0
empty configuration syntax check  -> +1
```

This excluded the private ASUS Edge collector configuration and SCL regex
content as necessary causes of the denial.

The installed Fedora source package for `pcre2-10.47-1.fc44.1` was then
inspected. Its spec enables JIT on x86_64 while explicitly disabling
`jit-sealloc`; the package comment records fork-safety concerns with that
SELinux-oriented allocator.

A temporary direct PCRE2 probe provided the final A/B evidence:

```text
unconfined_t:
PCRE2_CONFIG_JIT=1
PCRE2_JIT_TEST_ALLOC_RC=0

syslogd_t:
PCRE2_CONFIG_JIT=1
PCRE2_JIT_TEST_ALLOC_RC=-48
PCRE2_ERROR_NOMEMORY=-48
execmem AVC delta=1
```

The same binary therefore reproduced the executable-memory restriction
independently of the production syslog-ng configuration.

Engineering decision:

- keep SELinux Enforcing;
- do not grant `syslogd_t self:process execmem`;
- do not add a broad `dontaudit` suppression;
- use authoritative current-boot audit evidence in the verifier;
- accept only one exact documented `syslog-ng-main` / `syslogd_t` /
  `execmem` signature;
- treat repetition or any different SELinux denial/error as an acceptance
  warning;
- treat journal-based evidence only as an explicitly degraded fallback.

The current boot contains deliberate diagnostic-probe AVC records, so final
zero-warning physical acceptance for the new verifier must be performed after
the next clean reboot rather than by deleting or hiding audit evidence.


## Tailscale firewalld / syslog collector exact-state reconciliation

The live Fedora firewall was inspected after the syslog-ng boot-readiness and
SELinux investigations.

The dedicated `workstation-tailscale` zone remained `target=DROP`, bound
only to `tailscale0`, with no services, broad explicit ports, protocols,
sources, forwarding or masquerade. One intentional exception was present in
both runtime and permanent state: a rich rule allowing the ASUS Edge router's
single private Tailscale `/32` source to TCP/6514.

Important observations:

```text
firewall-cmd --query-port=6514/tcp -> no
runtime rich rules                 -> one source-restricted TCP/6514 rule
permanent rich rules               -> same rule
nftables zone allow chain          -> source /32 + tcp dport 6514 accept
syslog-ng listener                 -> Tailscale IPv4:6514
direct firewalld rules             -> none
```

This is intentionally not represented as a broad `6514/tcp` zone port.

Repository review found drift between that justified live state and the
existing exact-state installer: `network/tailscale-firewall-zone.sh` removed
all rich rules and required the list to remain empty. A restore or rerun could
therefore have broken remote logging.

The repository remediation keeps the private Tailnet address out of Git. If
the private ASUS Edge collector config is present, the firewall stage derives
its single IPv4 `/32` `netmask()`, requires it to be inside the Tailscale
IPv4 range, and converges to exactly one source-restricted collector rule.
When the collector config is absent, the original empty-rich-rule policy
remains in force.

The security verifier follows the same derived desired state and rejects any
additional or mismatched rich rule.


### Physical acceptance of the collector firewall path

The first physical application attempt failed closed during runtime target
validation because the local firewalld version did not return a usable runtime
value for the non-permanent `--get-target` query. The rollback restored the
previous firewall state successfully.

The branch was then corrected to read the runtime target from `--list-all`,
and the repository fixture was tightened so this behavior is represented in CI.

The second physical application completed successfully:

```text
APPLY_RC=0
target: DROP
tailscale0: dedicated interface
services: none
ports: none
forward: no
masquerade: no
runtime rich rule: exactly one collector source /32 -> TCP/6514
permanent rich rule: identical
broad query-port 6514/tcp: absent
syslog-ng: active
collector listener: present on Tailscale IPv4:6514
```

Final end-to-end acceptance was performed from the ASUS Edge router after the
exact-state policy had been reapplied. A unique `edge-e2e` marker generated
on the router appeared in the Fedora collector log, while syslog-ng remained
active and listening on TCP/6514.

This closes the firewall/collector path as physically validated without
publishing either endpoint's private Tailnet address.


## Clean-boot rfkill AVC contextual verification

The clean reboot exposed two audit events from `systemd-rfkill`, each
containing `dac_override` and `dac_read_search` denials.

Physical investigation showed that the associated PATH records represented
write-only `sysfs_t` objects (`mode=file,200`). Mapping their inodes on the
live host identified write-only `uevent` nodes belonging to the active Wi-Fi
driver/module.

The local rfkill state directory was correctly labelled and `restorecon -n`
reported no drift. `systemd-rfkill.service` exited successfully and the
physical Wi-Fi/Bluetooth rfkill state remained correct.

Upstream systemd explicitly treats privilege errors while reading a device
`uevent` attribute as non-fatal because those files may be write-only. The
Fedora SELinux policy permits `systemd_rfkill_t` to read sysfs generally but
does not grant the broad DAC override capabilities.

The verifier is therefore being tightened contextually rather than adding a
simple process-name whitelist. A systemd-rfkill capability event is accepted
only when all of the following are true:

```text
same audit serial contains both expected capability AVCs
PATH object type = sysfs_t
PATH mode = 0200
PATH is accessed through /proc/self/fd/N
failed syscall = openat/openat2 with EACCES
process/domain = systemd-rfkill / systemd_rfkill_t
recorded inode still resolves to a write-only sysfs uevent node
```

If any part of that context is absent, the denial remains unexpected and the
zero-warning acceptance gate fails.

This preserves fail-closed behavior while distinguishing the demonstrated
write-only sysfs probe from an unrelated future DAC problem.


## DING v99 managed-system lifecycle closure

A recurring DING regression was reproduced after the extension advanced from the
accepted v97 state to pristine upstream v99: repository-managed Polish desktop
menu strings and the `Monitor systemu` action were replaced by the normal
per-user extension update lifecycle.

The v99 source was audited from the exact official EGO archive:

```text
archive SHA-256:
f5f80d3371f00b7f3fd073d33c90f1c18750f006a284e76f37c1973685a33acc
```

The accepted design moves only DING out of the per-user auto-update path and
into:

```text
/usr/local/share/gnome-shell/extensions/ding@rastersoft.com
```

The builder verifies the source archive and pristine critical fingerprints
before mutation, applies the repository Polish catalog and exact v99 System
Monitor patch, compiles schemas, normalizes system-scope permissions, and
calculates the deterministic final tree hash. The accepted tree is:

```text
08a0c6e4ecb72c8e4693134c061cedfc88090054c98179de3dfd2fac2669a714
```

Two migration preflight defects were found and corrected fail-closed without
changing the live DING tree: an `XDG_DATA_DIRS` trailing-slash comparison and
root-owned staging permissions that initially made the integrity helper unable
to read the staged files.

The final migration created a rollback backup, installed the root-owned tree,
restored SELinux labels, removed the per-user DING copy and pending-update
copy, and required a GNOME logout/login before runtime acceptance.

Post-login validation confirmed:

```text

managed tree SHA-256 = 08a0c6e4ecb72c8e4693134c061cedfc88090054c98179de3dfd2fac2669a714
per-user copy = absent
pending update = absent
dedicated verifier = PASS
visual Polish desktop menu = PASS
```

The first full verifier exposed two unrelated desired-state drifts: an extra
GeForce NOW favorite mirrored into Dhruva order and Space Bar CSS reset to
zero-radius/zero-horizontal-padding. The repository baseline was not changed;
the workstation was reconciled back to the already accepted Dhruva and Space

Final physical acceptance:

## Dhruva GitHub archive supply-chain hardening

Issue #27 was resumed after the DING v99 managed-system lifecycle closure.

The accepted Dhruva runtime remains version 17 / 2.0 from upstream GitHub
commit:

```text
f8121f68fcef48c0324e8cd87fd30bf9a2131962
```

Two independent downloads of that exact GitHub commit archive were compared
before promoting any digest. Both downloads were byte-identical, parsed as
valid gzip tar archives, exposed the expected commit-root directory and
contained the expected Dhruva metadata.

Reviewed archive SHA-256:

```text
7baff8a0ecb44835fcb5edd7b7d23a4bc6765e24ed1125623dc7680b3ecd5733
```

The source lock now records both the exact 40-character Git commit and this
reviewed archive digest. The restore path verifies the digest before
`tar -xzf` and also checks that archive paths remain under the expected
`dhruva-<commit>` root and that `metadata.json` is present.

Repository consistency now requires a valid 64-character lowercase SHA-256
for every `github-commit` extension source. Static security fixtures cover a
valid archive, wrong digest, missing/invalid digest, wrong archive root,
unsafe member path and the invariant that verification occurs before
extraction.

This change intentionally fails closed if GitHub ever serves different bytes
for the same pinned commit archive. Such a change requires explicit review and
digest promotion rather than an automatic lock update.
