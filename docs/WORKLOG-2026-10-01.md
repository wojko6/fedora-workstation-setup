# Worklog — 2026-10-01

## Fedora syslog-ng / Tailscale boot readiness

A repeatable boot-order failure was investigated on the physical Fedora
workstation hosting the ASUS Edge syslog-ng collector.

### Observed failure

The collector binds TCP/6514 only to the workstation's Tailscale IPv4 address.

On two consecutive boots, `syslog-ng.service` started before that address was
assigned to `tailscale0`. The unit already declared ordering after
`tailscaled.service` and `network-online.target`, but that ordering was not
sufficient: systemd considered `tailscaled.service` started before the
Tailscale backend had reached its usable Running state and before the node IPv4
address was present.

The failure signature was:

```text
Error binding socket
Cannot assign requested address (99)
Error initializing message pipeline
```

The package unit's `Restart=on-failure` policy then retried quickly until the
systemd start limit was hit. A later manual start succeeded once Tailscale was
fully ready.

### Remediation

The accepted local drop-in now gates syslog-ng startup with Tailscale's own
readiness command:

```ini
[Unit]
Wants=tailscaled.service network-online.target
After=tailscaled.service network-online.target

[Service]
ExecStartPre=/usr/bin/tailscale wait --timeout=60s
ExecStartPre=/usr/bin/tailscale ip --assert=<current-node-tailscale-ip>
RestartSec=15s
```

The public repository does not store the real Tailscale IPv4 address. The
installer derives the current node IPv4 locally when the private
`/etc/syslog-ng/conf.d/asus-edge-collector.conf` is present.

Tailscale documents `tailscale wait` specifically for services that need to
bind to a Tailscale interface or IP. Fedora's installed Tailscale 1.98.8 CLI
provides the command, while the tested RPM did not ship
`tailscale-online.target`, so the drop-in calls the CLI readiness primitive
directly.

### Controlled reboot validation

After installing the readiness guard, a physical reboot produced the intended
sequence:

```text
tailscaled.service started
  -> Tailscale backend reached Running
  -> Tailscale IPv4 became available
  -> syslog-ng ExecStartPre checks passed
  -> syslog-ng started
  -> TCP/6514 listener present on the Tailscale IPv4
```

Observed acceptance state after reboot:

```text
syslog-ng ActiveState=active
syslog-ng SubState=running
Result=success
NRestarts=0
both ExecStartPre commands status=0
TCP/6514 listener present on Tailscale IPv4
current-boot bind/startup error search: empty
```

The service started only after Tailscale reported its peer API on the node
address and transitioned to Running.

### Scope and boundaries

This validates the boot-readiness dependency for the existing local collector.
It does not publish the collector's private Tailscale address, client
certificates, CA material, or other private logging configuration.

The unrelated package-unit warning about an unset `SYSLOGNG_OPTS` environment
variable remains a separate cleanup item because it did not cause the bind
failure and the service reached `Result=success`.
