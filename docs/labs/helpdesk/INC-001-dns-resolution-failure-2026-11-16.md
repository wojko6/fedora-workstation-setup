# INC-001 — DNS resolution failure: L1 troubleshooting lab

**Date:** 2026-11-16  
**Category:** Network / DNS  
**Priority:** P3 (training scenario; not a production SLA assignment)  
**Final status:** **RESOLVED — operator-verified**  
**Type:** Deliberately induced fault in an isolated virtual-machine configuration; **not** a customer or production incident.

## Scenario

> "My computer is connected to the network, but I cannot open websites."

The objective was to distinguish IPv4 reachability from DNS name resolution, find the misconfiguration, restore the original resolver settings, and validate that the reported symptom disappeared.

## Environment

- Hypervisor: Oracle VirtualBox **7.2.22** on a Fedora 45 KDE Wayland host.
- Guest: Debian GNU/Linux **13 (Trixie)**, minimal text-mode installation.
- VM: `Helpdesk-DNS-LAB-01`; **1536 MB RAM**, **2 vCPU**, **20 GB dynamic VDI**.
- Guest NIC: `enp0s3`, VirtualBox **NAT**, IPv4 **10.0.2.15/24**.
- Default route: **via 10.0.2.2**, from DHCP.
- Baseline DNS: **10.0.2.3** (VirtualBox NAT resolver; an additional IPv6 resolver was listed).
- Guest SSH service: `active`.
- Pre-exercise VirtualBox snapshot: **CLEAN-BASELINE**, explicitly confirmed by the operator in the snapshot manager.
- The separate `Fedora-DR-Test` virtual machine, host DNS, router and Pi-hole were left unchanged.

> VirtualBox NAT is **not** equivalent to a completely air-gapped environment; the exercise limited modifications to the guest resolver configuration. No DNS or DHCP changes were made on the host or the LAN.

## Baseline observations

The guest had a DHCP lease, a default route, working DNS and IPv4 connectivity:

| Check | Observed result |
| --- | --- |
| IPv4 interface | `enp0s3` UP; `10.0.2.15/24` |
| Default gateway | `10.0.2.2` |
| DNS configuration | `10.0.2.3` |
| `getent ahostsv4 debian.org` | Returned IPv4 addresses |
| `ping 1.1.1.1` | Successful, zero loss |
| SSH | `systemctl is-active ssh` → `active` |

## Fault injection (controlled)

After obtaining a root shell with `sudo -i`, the operator confirmed that `/etc/resolv.conf` was a regular file. It was generated by `dhcpcd` on the guest. The original file was backed up:

```bash
cp -a /etc/resolv.conf /root/resolv.conf.INC-001.bak
```

The test replaced the guest's resolver with a loopback address where no local DNS server had been configured:

```bash
printf 'nameserver 127.0.0.1\noptions timeout:1 attempts:1\n' > /etc/resolv.conf
```

This was a **temporary and intentionally invalid DNS setting**. The network address and routing configuration were not modified.

## Incident diagnosis

| Test | During induced fault | Interpretation |
| --- | --- | --- |
| `ip -4 addr show enp0s3` | NIC UP; `10.0.2.15/24` | Guest NIC and DHCP IPv4 address present |
| `ip -4 route` | Default route via `10.0.2.2` | Gateway route present |
| `ping -c 2 -W 2 1.1.1.1` | **2/2 received, 0% packet loss** | External IPv4 reachability worked |
| `getent ahostsv4 debian.org` | **No address output** | Name resolution failed |
| Resolver command exit status | **2** | Failure was confirmed programmatically |
| `cat /etc/resolv.conf` | `nameserver 127.0.0.1` | Resolver pointed to a nonfunctional local endpoint |

**Root cause:** the guest resolver was deliberately redirected from the working VirtualBox NAT DNS service to `127.0.0.1`. No suitable DNS resolver was configured on the loopback address for this exercise. The observed fault was **DNS name resolution**, not a loss of IP reachability.

## Resolution

The operator restored the saved resolver file:

```bash
cp -a /root/resolv.conf.INC-001.bak /etc/resolv.conf
```

The restored configuration again listed `nameserver 10.0.2.3` (and the previously present IPv6 resolver).

## Post-fix validation

| Test | Observed result | Status |
| --- | --- | --- |
| `getent ahostsv4 debian.org` | Returned multiple IPv4 addresses, e.g. `151.101.194.132` | **PASS** |
| `echo "DNS_EXIT_CODE=$?"` immediately after `getent` | `DNS_EXIT_CODE=0` | **PASS** |
| `ping -c 2 -W 2 1.1.1.1` | **2/2 received; 0% packet loss** | **PASS** |
| Resolver contents | Original `10.0.2.3` restored | **PASS** |

**Decision:** `INC-001=RESOLVED`. The test reproduced an expected user complaint, identified the deliberately introduced DNS misconfiguration, restored the baseline resolver and verified successful DNS lookup with unchanged IP connectivity.

## Service Desk closure note

**Issue:** User cannot access websites by hostname despite appearing to be connected to the network.  
**Impact:** Loss of hostname-to-address resolution inside one laboratory VM.  
**Diagnosis:** IPv4 address and default gateway were present. External ping by IP succeeded, while DNS lookup failed with exit status 2.  
**Cause:** Incorrect `/etc/resolv.conf` resolver pointing to `127.0.0.1`.  
**Fix:** Restored the previously saved DHCP-managed DNS configuration.  
**Verification:** DNS lookup returned an exit code of 0 and addresses; IP ping succeeded with 0% packet loss.  
**Outcome:** Resolved. No host, router, Pi-hole or unrelated VM modifications.

## Lessons learned

1. Test **IP reachability and name resolution separately**. A successful ping to a numeric IP address does not prove DNS works.
2. Check the interface, DHCP lease, default route and configured resolver before changing network settings.
3. Preserve the original configuration and an appropriate VM snapshot before fault injection.
4. Prefer a narrow, reversible fix and repeat the failed test to demonstrate recovery.
5. A successful isolated training incident is evidence of **hands-on lab practice**, not evidence of employment-based Service Desk experience or a production deployment.

## Evidence and limitations

- Source evidence: screenshots and console output supplied by the operator in the 2026-11-16 conversation; no unredacted screenshots or local logs were committed to the public repository.
- The diagnostic test covered name resolution via `getent`, IPv4 reachability via ICMP, a single VM and a short post-fix interval. It was not a browser test, DNSSEC test, repeated endurance test or broader network certification.
- `/etc/resolv.conf` was generated by `dhcpcd`; future lease renewals might overwrite a temporary edit. This does not change the observed results of the controlled exercise.
- The VM snapshot is a recovery point within VirtualBox, **not** an independent off-host backup.

## Relevance to entry-level IT roles

The exercise demonstrates a structured approach to common Helpdesk / Service Desk L1 troubleshooting: capturing a symptom, verifying network layers, identifying a DNS failure, applying a reversible correction, confirming the fix, and writing an incident closure note.

**CV-safe wording (English):** "Completed a hands-on Debian/VirtualBox troubleshooting lab: diagnosed a simulated DNS resolution failure using `ip`, `ping` and `getent`; restored resolver configuration and documented verification results."
