## Administrative Wi-Fi identity and ASUS services

A diagnostic initially found Fedora associated with the separate 2.4 GHz SSID,
using a different LAN address from the authorized administration workstation.
ASUS WebUI/SSH timed out there while the host could still ping the router.
This was reconciled with the existing **source-restricted management allowlist**
in the ASUS Edge Gateway project (Issue #127), not treated as a KDE regression.

After connecting Fedora to the authorized 5 GHz profile:

- router HTTPS via its configured certificate hostname returned HTTP 200;
- router SSH on the configured private port returned `ASUS_SSH_OK` and exit 0;
- `asus-traffic-importer`, `dns-guard-monitoring`,
  `pihole-dns-collector` and `routercloud-sync` each subsequently
  reported `Result=success`, `ExecMainStatus=0`;
- the 5 GHz NetworkManager connection was set to autoconnect priority 50,
  with the 2.4 GHz connection retained at priority 0 as a fallback;
- a later fresh KDE login retained the authorized 5 GHz connection,
  Tailscale active and zero failed user units.

**Boundary:** 2.4 GHz fallback is not equivalent to authorized administrative
access. The project-owned ASUS firewall and source allowlist were **not**
weakened or changed. No private SSIDs, MACs, address reservations, Tailnet IPs,
passwords or keys are published in this report.

## GNOME Shell abort during desktop transition

A single current-boot GNOME Shell abort was timestamped **2026-10-10 11:23:59 CEST** (the coredump was journaled at approximately 11:24:01):

```text
process: /usr/bin/gnome-shell
PID: 1935
signal: SIGABRT
coredump: present
stack: dump_gjs_stack_on_signal_handler
       -> X11 event handling / Mutter
```

Other contemporaneous journal entries include a duplicate
`org.freedesktop.FileManager1` D-Bus activation name, a GNOME login worker
SELinux status-query denial, and a GNOME Keyring/GDM control-file message.
**None has been proven to cause the abort.** The stack alone does not provide
a definitive root cause. The currently running KDE KWin/Plasma processes have
not been shown to crash; both are active and the live failed-unit lists are
empty.

**Follow-up coredump/journal investigation (same day).** The coredump
metadata attributes the abort to **PID 1935 / UID 1000**, command
`/usr/bin/gnome-shell --mode=user`, with user unit
`org.gnome.Shell@user.service`, timestamp **11:23:59 CEST**.
This was a user GNOME Shell, **not** the subsequent GDM greeter Shell.

Chronology extracted from the bounded current-boot journal:

- **11:23:59:** the outgoing user's GNOME Shell coredump was timestamped;
- **11:24:01:** `gdm-autologin`/PAM closed the previous user session
  successfully; `systemd-coredump` and KDE DrKonqi also emitted
  crash-processing messages during session turnover;
- **11:24:01–11:24:02:** logind created the `gdm-greeter` Wayland session;
- **11:24:02:** `gnome-session-init-worker gnome-login` hit an SELinux
  `status` permission denial on `graphical-session.target` while the
  greeter session was being initialized, after the user-shell abort;
- **11:24:02–11:24:03:** separate GDM greeter GNOME Shell **PID 8852**
  started as a Wayland display server, registered with GDM and reached
  GNOME session targets.

This supports a **user GNOME Shell abort temporally associated with session
termination/transition**, followed by successful GDM greeter startup. It does
**not** prove logout caused the abort or reveal the original internal trigger;
the `dump_gjs_stack_on_signal_handler` and Mutter/X11 frames are not enough
to assign root cause. The subsequent greeter SELinux denial must not be
misattributed as the earlier crash's cause. The ABRT notification mentioning
another PID is not proof of another current-boot coredump.

**Additional process-scoped journal evidence.** `journalctl -b _PID=1935`
showed the GNOME user session entering Wayland/NVIDIA startup at **11:23:34**,
loading installed GNOME extensions (including search bar, tiling, DING, user
theme and DDC/CI display-brightness), and reporting non-fatal Shell/extension
warnings. At **11:23:54** the Shell logged several GVFS volume-monitor
disconnections and **`Connection to xwayland lost`**; at **11:23:59** it
reported `SIGABRT` and a GJS stack trace. The GDM PAM session-close message
followed at **11:24:01**. This narrows the incident to the GNOME user-session
transition/teardown; neither the Xwayland disconnect nor any extension can be
declared the root cause on timing alone.

The attempted system-manager query
`journalctl -b -u org.gnome.Shell@user.service` returned no entries.
This does **not** mean the user unit was absent: it is a user service and its
logs can be inspected by user-journal/structured fields instead.

**Next bounded investigation:** if this recurs, inspect the GNOME user-session
journal before the abort and a symbolized coredump, then validate normal
GNOME login/logout as a fallback. Do not disable SELinux, switch display
managers, remove GNOME extensions wholesale, or change NVIDIA/kernel
parameters on the present evidence.

## AK820 keyboard — intermittent startup USB enumeration failure

The `SONiX AK820` keyboard (`0c45:8009`) was physically connected to a rear
laptop USB port during recurring failures to type immediately after startup.
The behavior had also occurred under GNOME, prior to this KDE migration.

The failed current-boot sequence on `usb 1-2.1` included four
`device descriptor read/64, error -32` lines, failed address assignment with
`error -71`, and `unable to enumerate USB device`. That USB path traverses
a visible `GenesysLogic` USB2.1 hub (`05e3:0610`). The keyboard later
enumerated successfully on the same path after operator intervention.

After physically moving the keyboard to a **side laptop USB port**, the
device enumerated at `usb 3-2`, on a separate root-hub/controller path
without that intermediate USB hub. It was operational, and
`power/control=on` was observed.

Five earlier boot-log samples showed successful AK820 enumeration on the
rear path; they **do not** prove that typing worked on those boots.
The current sample contains the enumeration errors and the successful
post-reconnection detection.

**Disposition:** keep the side port for several normal cold boots/restarts
and record whether the keyboard works before login. No USB autosuspend,
udev, kernel boot parameter, BIOS or controller changes were applied.
Successful detection after plugging in is not yet proof of a permanent fix.
