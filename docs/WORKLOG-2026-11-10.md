# Worklog — 2026-11-10

> **Scope:** physical Fedora 44 → 45 migration, KDE/NVIDIA, recovery readiness, VirtualBox and observability on a Lenovo Legion 5 laptop.
> **Evidence:** operator-supplied command outputs and Grafana Explore screenshots; GitHub documentation review. This is not a clean-room Fedora 45 restore or a complete long-term stability certification.
> **Publication:** sanitized, documentation-only; no credentials, internal addresses, backup secrets or full log payloads.

## 1. Controlled major upgrade — physical host

- **Executed on the physical workstation:** Fedora 44 was migrated to **Fedora 45** using a reviewed offline DNF5 system-upgrade transaction (approximately **3,683 packages**, about **6.8 GiB** downloaded).
- **Observed after reboot:** Fedora 45, kernel **7.3.3-300.fc45.x86_64**, **KDE Plasma 6.8.2 / Wayland** and **NVIDIA 620.70.06 Open Kernel Module** on the laptop RTX 3060. The external DisplayPort monitor was active after boot. KDE and the operator's dock were functional.
- Previously held Fedora 44 NVIDIA 610 exact-version package locks were removed as part of the reviewed transition. This is not a blanket approval to remove version locks in other environments.
- **Scope:** the running host was upgraded; the repository's **Fedora 44 / GNOME 50.5 reproducible restore baseline remains historical and unpromoted to Fedora 45**. Neither a Fedora 45 clean-room installation nor the complete GNOME/KDE desired-state verifier was run after upgrade.

## 2. Recovery preparation and rollback boundaries

- Before migration the operator prepared separate Btrfs read-only snapshots, a new local restic recovery snapshot and retained prior independent external backup generations.
- A restic repository structural check, a bounded **1% data check**, and selected recovered-file checksum comparisons passed. This is **not** a full data scrub, trial restoration to an empty drive, or a boot-tested rollback.
- Keep pre-upgrade backups; the old-release package downgrade is **not** a validated rollback strategy for a major OS transition.

## 3. GPU, display and suspend/resume

- Confirmed NVIDIA 620.70.06 remained available to `nvidia-smi` after a real **deep/S3 suspend and resume**. The DisplayPort output was still connected and enabled. `nvidia-suspend.service` and `nvidia-resume.service` completed successfully.
- The kernel reported one `NV_ERR_NO_MEMORY` from `_memdescAllocInternal` while entering suspend. The operating system resumed successfully; no NVIDIA Xid was found in the inspected cycle. A bounded audit showed no matching SELinux AVCs.
- RAM, GPU memory and `/var/tmp` filesystem free-space checks taken **after** resume did not indicate exhaustion. They do not establish memory availability at the exact failure time.
- **Result:** `SUSPEND_RESUME=PASS_WITH_WARNING`. Repeated-cycle and longer-term regression testing remain open. Existing NVIDIA VRAM-preservation settings were **not changed**.

## 4. ASUS log pipeline and existing DNS monitoring

- Confirmed syslog-ng listening over the existing Tailscale path and writing to a local dated router log. A previously established systemd startup/readiness override preserved startup behavior.
- **Executed change:** added a dedicated `loki.source.file "asus_router"` target to the existing Grafana Alloy configuration, with scoped ACL read access to router logs. The existing Pi-hole source remained intact.
- `alloy validate` succeeded and Alloy restarted successfully. The `asus_router` reader reported three active files; its read-line metric and Loki's `{source="asus-router"}` query showed ingestion.
- **Grafana Explore visual confirmation:** **66 ASUS entries** in the selected hour and roughly **17.2k Pi-hole entries** represented in the Pi-hole log-volume chart. Counts are bounded by the selected query window and UI limits; they are not lifetime or delivery-SLA measurements.
- **No firmware, router service or router configuration change** was executed during this monitoring work. No persistent compatibility claim is made for a future reinstall until Alloy and syslog-ng deployment are covered by desired-state code.

## 5. VirtualBox on the target kernel

- VirtualBox **7.2.22 (RPM Fusion)** loaded `vboxdrv`, `vboxnetflt` and `vboxnetadp`; module vermagic matched the running Fedora 45 kernel.
- The existing EFI-based test VM started successfully and reached the VirtualBox UEFI boot manager. Its dynamically allocated VDI was approximately 2 MiB on disk and UEFI reported no bootable operating system.
- **Result:** hypervisor start / firmware execution **PASS**; guest operating-system boot, installed guest networking and end-to-end DR restore **NOT TESTED**.

## 6. KDE IMSettings autostart cleanup

- A user session showed the generated `app-imsettings\\x2dstart@autostart.service` failed because `imsettings-boot.sh` declared the KDE/Wayland environment unsupported.
- **Executed per-user change:** added an XDG autostart override containing `Hidden=true`; reloaded the user systemd manager and reset the old failed state.
- **Observed:** zero failed user units, generated unit `not-found/inactive/dead`. System-wide autostart files and packages were untouched; the daemon was not deliberately stopped.
- **Open:** persistence should be checked after the next normal login.

## Remaining gates / next actions

1. **Physical Fedora 45 operational smoke test: PASS_BOUNDED**, not complete release certification.
2. **Reproducible Fedora 45 / KDE desired-state promotion: HOLD** until project manifests, static checks, clean-room restore and full physical validation are rebuilt for this target.
3. Monitor whether the single `NV_ERR_NO_MEMORY` warning recurs after ordinary suspend cycles; preserve known working settings meanwhile.
4. Recheck IMSettings after login; test full VirtualBox guest boot when installation media or a populated guest is available.
5. Retain verified backups until rollback and application-level stability are sufficiently demonstrated.
