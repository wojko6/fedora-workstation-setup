## Problem statement and previous evidence

With NVIDIA 615.71.09, the workstation previously lost usable video on both displays during suspend/resume attempts; kernel logs included `kgmmuInvalidateTlb_GM107` failures, `NV_ERR_INVALID_STATE`, GSP RPC trouble and a `Lost display notification` message in affected runs. An earlier 2026-10-10 `s2idle` cycle had succeeded, but later testing demonstrated that neither `deep` nor `s2idle` could be considered reliably safe with 615.71.09. Root-cause attribution to NVIDIA is still an inference, not a confirmed upstream defect.

A controlled rollback to the earlier RPM Fusion build `610.57.04-1.fc44` was selected as a diagnostic and potentially stabilizing change, with explicit return-to-615 capability.

## Verified package provenance and rollback readiness

1. The correct HTTPS RPM Fusion mirror host was `ftp.fi.muni.cz`. Using `ftp.muni.cz` and a separate archive hostname initially failed certificate-hostname validation; TLS verification was **not** disabled. The three main 610 RPM URLs on the correct host returned `HTTP=200 SSL_VERIFY=0`.
2. **12 matching NVIDIA 610 RPMs** were downloaded to a local user Downloads staging directory (534 MiB). They covered `akmod-nvidia`, `nvidia-modprobe`, `nvidia-persistenced`, `nvidia-settings`, `xorg-x11-drv-nvidia`, CUDA components, kernel-module source, power support, and relevant x86_64/i686 libraries. Every `rpm -Kv` passed OpenPGP signatures and package digests. The observed signing-key fingerprint was `79bdb88f9bbf73910fd4095b6a2af96194843c65`.
3. **12 currently installed NVIDIA 615 RPMs** (547 MiB) were separately downloaded and passed `rpm -Kv` checks. **Three locally built 615 `kmod-nvidia` RPMs** for kernels 7.2.7, 7.2.8 and 7.2.9 were copied from the akmods cache. All three backups passed byte-for-byte comparison with the originals.
4. A copy-and-compare command was provided for the current kernel initramfs before the actual downgrade, but its execution result was **not separately shown** in the conversation. Therefore **the presence and integrity of an initramfs backup remain unverified** and must not be claimed as a completed recovery gate.
5. DNF5 dry-run using `sudo dnf --assumeno install --allowerasing <610-RPMs>` proposed **12 downgrades** and removal of only **3 older 615 kernel-specific kmod packages**. No unrelated removals were proposed.
6. A corresponding `--assumeno` invocation for the 615 recovery set, including the three cached kmod RPMs, reported all **15 already installed** in the pre-downgrade environment. This confirmed staging and syntax but did **not** independently exercise post-610 recovery.
7. The certificate path appeared missing to an unprivileged test because the containing directory was restricted to `root:akmods`. Privileged inspection confirmed the DER file exists. `mokutil --test-key` printed `is already enrolled` but returned status 1 on this host. A separate `mokutil --export` and byte-for-byte DER comparison returned `MOK_EXPORTED_EXACT_MATCH=PASS`. The current module signer matched the enrolled certificate.

### Failed automation attempt — important safety lesson

An initial TTY rollback script stopped GDM before issuing a DNF5 command that placed `--allowerasing` before `install`. DNF rejected that command and also rejected the scripted restore attempt. **No package transaction ran.** GDM then showed a blank greeter background despite being active.

TTY access remained available; RPM queries still showed NVIDIA 615.71.09. A controlled reboot restored a working KDE Wayland graphical session and `nvidia-smi` confirmed NVIDIA 615 was still active; NetworkManager and Tailscale remained active.

The faulty script was **renamed with a `.BROKEN` suffix** and is not approved for reuse. The corrected `dnf install --allowerasing ...` commands were separately dry-run before the actual install. This failure shows why preflight/plan verification must be completed **before** stopping a live display manager, why command syntax should be validated with the exact intended action, and why rollback procedures need independent failure-path tests. The actual successful downgrade was carried out manually from a working TTY, **not** with the disabled script.

## Controlled deep suspend/resume tests

Both attempts used the standard systemd suspend path with a scheduled RTC alarm:

```bash
sudo rtcwake -m no -s 120 && sudo systemctl suspend
```

| Cycle | `PM: suspend entry (deep)` | `PM: suspend exit` | User-visible result | Lock greeter |
| --- | --- | --- | --- | --- |
| 1 | 12:17:14 | 12:17:53 | GPU and KDE usable again | **SIGSEGV** at 12:17:59, PID 7241 |
| 2 | 12:31:50 | 12:33:57 | GPU and KDE usable again | **SIGSEGV** at 12:34:03, PID 9252 |

All timestamps are **2026-10-11 CEST**. After testing, `nvidia-smi` continued to report 610.57.04 (a temperature reading of 37°C was observed after the first wake). The inspected kernel wake windows did not show the earlier NVIDIA 615 NVRM/GSP failure signature.

**Important distinction:** The kernel and GPU resumed twice, but `kscreenlocker_greet` crashed in **2/2** attempts. Do not mark KDE suspend/lockscreen reliability as PASS.

### Exact repeated crash

Each resume caused many Qt applications to emit `There are no outputs - creating placeholder screen` (approximately 12:17:56–12:18:00 and 12:34:00–12:34:04). KWin reported:

```text
Greeter Process encountered an unhandled error: QProcess::Crashed
Greeter process exit unregular. Restarting lock.
```

The kernel logged `kscreenlocker_greet` signal **11** in `libPlasmaQuick.so.6.7.5`, in both cases at relative offset **0x36fe1** (fault address `0x35`). `eu-addr2line` identified this location as:

```text
PlasmaQuick::SharedQmlEngine::rootObject() const
/usr/include/c++/16/bits/atomic_base.h:518:24
```

Upstream KDE `libplasma` v6.7.5 defines `rootObject()` as a return of `SharedQmlEnginePrivate::rootObject`, stored as `QPointer<QObject>`. The repeatable fault points to this code path, **not** to a proven lifetime/race root cause.

A manual screen-lock test using `Meta+L` and password unlock worked without matching new journal failures. The failure is therefore reproducible during the tested resume path, not during the tested ordinary lock/unlock path.

### Additional display evidence and limits

- Laptop lid state: `closed` throughout normal use and testing.
- Only external monitor `DP-2` is enabled at 2560×1440 @ 180 Hz. The internal `eDP-1` is connected but disabled on purpose.
- At 12:34:02, PowerDevil/libddcutil emitted a `DDCA_EVENT_DISPLAY_CONNECTED` and `DDCA_EVENT_DDC_ENABLED` **for internal `eDP-1`**, not the external `DP-2`. The journal excerpt does **not** prove a physical DP disconnect.
- A separate burst of Qt no-output warnings at 12:38:49–12:38:50 occurred **about five minutes after** the second kernel resume and must not be confused with the immediate post-resume burst at 12:34.
- `rpm -V` for `kscreenlocker`, `libplasma`, `plasma-workspace`, `kwin`, `qt6-qtbase`, `qt6-qtwayland` and `qt6-qtdeclarative`: **RC=0**; no integrity differences reported.
- No newer versions of those packages were returned by `dnf list --upgrades` in the enabled repositories at the time of inspection.
- `coredumpctl` found no crash dump. The `systemd-coredump.socket` was active and the current shell's core limit was unlimited, but upstream `kscreenlocker` v6.7.5 calls `prctl(PR_SET_DUMPABLE, 0)` to protect the credential-handling greeter. **Do not weaken this security setting or upload potentially sensitive core dumps by default.**
- The absence of a full backtrace limits precise root-cause attribution. The fault offset, symbol and journal snippets still provide reproducible upstream evidence.
